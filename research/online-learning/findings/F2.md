# F2 — Fast CPU Inference for Small Language Models (sub-10M, CPU)

Scope: techniques and runtimes for sub-10M (and near-edge) models on CPU. Evidence from 2024–2026 papers/benchmarks. Target project: RecaMem byte-RTU / droid engine (CPU-only, local-first).

## 1. Quantization (INT8/INT4) on CPU

- INT8: ~1.5–2x latency speedup vs FP16, ~50% memory; LLM.int8() outlier-channel mixed path; SmoothQuant needs calibration data.
- INT4 weight-only: ~75% memory cut, up to ~8.5x latency speedup with GPTQ/AWQ; quality drift on reasoning/code; validate on own prompts.
- KV cache quantization: INT8 KV halves KV bytes vs fp16 (solid default); INT4 KV task-sensitive (reasoning/code drift).
- CPU-specific: Intel Extension for Transformers (IET) provides auto INT4 weight-only quant flow + optimized kernels; ORT GenAI supports CPU execution providers + KV cache + constrained decoding.
- Format choice: target runtime's best-optimized kernel (e.g. llama.cpp Q4_0) rather than theoretically better format at lower throughput (Daedalus finding).

## 2. BitNet ternary (1.58-bit)

- Weights in {-1,0,+1}: log2(3)=1.58 bits/weight; matmul becomes add/sub/skip; ~0.4 GB for 2B vs 6 GB FP16.
- bitnet.cpp: optimized kernels for x86/ARM (I2_S lossless 2-bit unpack; TL1/TL2 LUT, AVX2/NEON); BitNet-b1.58-2B-4T (2.4B), plus 270M/600M embedding models.
- Bench (2B): 28.7 tok/s CPU vs 15.3 tok/s GGUF Q4_K_M; 1.4 J/tok; energy-efficient.
- Caveat: must be natively trained ternary; PTQ to ternary fails; sub-10M ternary training unproven at quality.

## 3. Linear attention / state-space / hybrid

- RWKV: RNN-like linear time, constant space, no KV cache; RWKV-7 (Goose) dynamic state; 0.1B–14B; GGUF weights; runs on phone; 10–100x lower compute for long ctx.
- Mamba / Mamba-3: selective SSM, linear complexity; Mamba-3 (2025) beats Mamba-2; hybrid with attention common (Jamba, Samba, Zamba).
- Linear attention (BASED, GDN): balances recall vs throughput.
- Daedalus-150M (2026): CPU-first hybrid, 12 short conv (2-timestep state) + 6 attention; 47.31 five-task vs 42.20 bar; decodes 1.76x faster at 2048 ctx (2.08x vs external peer); 1.17x predicted by bandwidth alone → residual is latency/cache locality.
- Key lever: ratio of cache-free (conv/recurrent) to attention layers is dominant deployable variable at batch-size-1 CPU.

## 4. Speculative decoding

- Draft small model proposes tokens, target verifies in one forward pass; lossless latency optimization.
- llama.cpp supports speculative decoding (--spec-type); best on code/structured extraction; needs shared tokenizer; VRAM headroom for draft.
- For sub-10M targets: draft+target both tiny; benefit mainly when draft is much smaller and aligned; otherwise overhead.
- Online speculative decoding (UC Berkeley 2025) adapts draft during serving; Intel/Weizmann: any small draft accelerates any LLM regardless of vocab (up to 2.8x).
- CPU-specific: limited optimized impl in llama.cpp (issue #21453); speculative can backfire on already-fast small targets.

## 5. ONNX Runtime (CPU)

- ORT 1.17+: graph fusions, kernel optimizations; Phi-2/Mistral/CodeLlama; INT4/FP16 paths beat PyTorch and llama.cpp for Phi-2.
- ORT GenAI: generation loop, token processing, sampling, KV-cache, constrained decoding; CPU + OpenVINO/QNN/DirectML/TensorRT RTX EPs.
- Olive: hardware-aware optimization pipeline.
- Tweak order: EP selection → IOBinding → graph opts (ORT_ENABLE_ALL) → quantization (dynamic INT8 → static/weight-only) → KV cache via GenAI → threading/memory.

## 6. llama.cpp optimization (CPU)

- Flags: -t/-tb (threads gen/batch), -ctk/-ctv (KV cache quant q8_0 safe), -fa (flash attention, prereq for KV quant), -b/-ub (batch), --no-mmap/--mlock, -ngl 0 for CPU.
- Quant types: Q4_0/Q4_K_M, IQ2/IQ1, TQ1_0/TQ2_0 ternary (1.69 bpw).
- Build: -DGGML_LTO=ON, -DLLAMA_BUILD_TESTS=OFF, AVX2/AVX-512/FMA.
- KV cache q8_0 both K/V safe with <0.1 ppl increase; q4_0 V risky.
- Merge-QKV when offloading attention to GPU; MoE expert offload flags.
- Apple Silicon: Metal FA kernel, q8_0 KV, no --no-kv-offload.

## 7. Architecture-level CPU co-design (cflow)

- Single-token decode is memory-bandwidth-bound: ~4 FLOP/byte vs ~20 machine balance; latency ≈ bytes(all weights)/BW.
- cflow: tile-native weights (128x256 Q4, ~18KB L2 tiles), fused projections, conditional expert loading, AVX2 kernels; 5.94 tok/s on 30.9B MoE vs llama.cpp 4.75 on dense.
- Pipeline-native transformers: dense_delay/expert_delay relax layer DAG → vertical stage-major schedule → 2.00x critical-path bandwidth reduction (9.00→4.50 MB/token) at +0.24 ppl.
- Tile layout: 7.29x fewer L1-d misses vs row-major.
- Negative results: PREFETCHT0 refuted (storage-bound), stage-major disk layout inconclusive.

## 8. Sub-10M / edge specifics

- MobileLLM-R1 / R1.5: 2-5x better reasoning at 2x smaller, mobile CPU.
- CITRAS-FM: 7M params, sub-0.1s CPU inference (time series).
- Daedalus-150M beats GPT-2 124M/Pythia-160M on 7x less data.
- MobileDets-style NAS: regular convs placed strategically boost CPU latency-accuracy.
- Structured sparsity (SRigL): 3.6x/2x faster CPU at 90% sparsity.

## 9. Recommendations for RecaMem (byte-RTU, CPU-only, local-first)

- Quantize byte-RTU weights to INT4 (Q4_0) or INT8; keep KV cache INT8; target llama.cpp/ORT GenAI CPU EP.
- For sub-10M models, prefer hybrid arch (conv/recurrent majority + few attention) for flat decode cost vs context (Daedalus pattern); avoid full attention in all layers.
- Consider BitNet ternary only if training from scratch with QAT; bitnet.cpp for 270M+ models; too heavy for <10M? ternary training infra cost.
- Speculative decoding: only if a much smaller aligned draft exists; otherwise skip (overhead).
- Use ORT GenAI for cross-platform CPU deployment; Olive for quantization.
- Measure with bandwidth model: bytes/token = W + 2*La*hkv*dh*b*t; optimize La and hkv (GQA) first.
- Keep fail-loud (no mock fallback) per project rules; no hard-delete facts.
