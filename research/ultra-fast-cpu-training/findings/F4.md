# F4: High-throughput CPU engine optimizations and hardware acceleration

## Findings

### [1] Intel AMX delivers a theoretical 3,482 GFLOPS per core for BF16 matrix operations, providing a 16x compute multiplier over AVX-512 (217 GFLOPS per core) and scaling to 195 TFLOPS across a 56-core Sapphire Rapids package.
- quote: "Theoretical performance: 3,482 GFLOPS per core (16 times that of AVX512)"
- url: https://blog.us.fixstars.com/intel-amx-advanced-matrix-extension-explained-introduction
- source_type: secondary
- published: 2025-09-10
- confidence: high

### [2] Real-world matrix multiplication benchmarks demonstrate that single-core AMX achieves an 11.7x speedup over AVX-512 in OpenBLAS GEMM, but parallel multi-core scaling on 112 cores drops to 2x due to memory bandwidth and thermal constraints.
- quote: "In our OpenBLAS benchmark it was 11.7x faster than AVX-512 on a single core and 2x faster across 112 cores."
- url: https://blog.us.fixstars.com/intel-amx-advanced-matrix-extension-explained-introduction
- source_type: secondary
- published: 2025-09-10
- confidence: high

### [3] Intel Extension for PyTorch enables native AMX hardware acceleration for BF16 training and inference by automatically dispatching to TMUL hardware through oneDNN and PyTorch autocast.
- quote: "Intel AMX is a built-in accelerator found on each 4th Gen Intel Xeon processor core, and it helps accelerate deep learning training and inference workloads."
- url: https://www.intel.com/content/www/us/en/developer/articles/technical/accelerate-pytorch-training-inference-on-amx.html
- source_type: primary
- published: 2024-02-14
- confidence: high

### [4] Under PyTorch 2.8.0 on AWS 8th-generation Xeon instances (m8i.4xlarge), BF16 AMX acceleration achieves batched inference throughput of 127.8 tokens/sec on Gemma-3-1b-it, 355.9 tokens/sec on DialoGPT-large (762M), and 415.1 tokens/sec on DeepSeek-R1-Distill-Qwen-1.5B at batch size 32.
- quote: "BF16(AMX) batch size 32 reaching the highest overall throughput at 415.1 tokens/sec"
- url: https://aws.amazon.com/blogs/compute/accelerate-cpu-based-ai-inference-workloads-using-intel-amx-on-amazon-ec2
- source_type: primary
- published: 2026-03-30
- confidence: high

### [5] Autoregressive decoding at batch size 1 incurs severe relative performance degradation on AMX because tile setup instructions (such as `ldtilecfg`) create fixed latency overheads that exceed acceleration gains unless amortized across batch sizes of 8 to 32.
- quote: "At batch size 1, DialoGPT-large’s autoregressive decoding generates tokens sequentially, producing many small matrix operations where AMX tile setup overhead exceeds the acceleration benefit. At batch sizes 8 and above, multiple sequences are processed in parallel, creating larger matrix operations that amortize this overhead and deliver 21-30% improvement."
- url: https://aws.amazon.com/blogs/compute/accelerate-cpu-based-ai-inference-workloads-using-intel-amx-on-amazon-ec2
- source_type: primary
- published: 2026-03-30
- confidence: high

### [6] TorchInductor's CPU compiler backend generates fused C++/OpenMP kernels with explicit vectorization and oneDNN/MKL weight prepacking, outperforming eager PyTorch by 1.16x to 1.26x on multi-threaded Hugging Face benchmarks.
- quote: "The TorchInductor CPU backend is sped up by leveraging the technologies from the Intel® Extension for PyTorch for Conv/GEMM ops with post-op fusion and weight prepacking, and PyTorch ATen CPU kernels for memory-bound ops with explicit vectorization on top of OpenMP-based thread parallelization."
- url: https://dev-discuss.pytorch.org/t/torchinductor-update-4-cpu-backend-started-to-show-promising-performance-boost/874
- source_type: primary
- published: 2022-11-24
- confidence: high

### [7] Consumer desktop CPUs on dual-channel DDR5-6000 are constrained by ~96 GB/s memory bandwidth, limiting single-stream generation throughput to 11 to 17 tokens/sec for 7B–8B models regardless of CPU core count.
- quote: "For local LLM inference, token generation speed is set by memory bandwidth, not CPU core count: a system generates roughly (memory bandwidth ÷ active bytes per token) tokens per second. That is why a quad-channel Ryzen AI Max+ 395 at 256 GB/s (AMD vendor spec) outruns a 16-core Ryzen 9 9950X on dual-channel DDR5-6000 at roughly 96 GB/s theoretical peak by more than 2× on the same model"
- url: https://www.compute-market.com/blog/best-cpu-for-local-llm-2026
- source_type: secondary
- published: 2026-09-13
- confidence: high

### [8] Compute-bound workloads such as prompt prefill and training backpropagation bypass memory streaming limits by utilizing CPU SIMD/tile matrix multiply units directly, achieving orders-of-magnitude higher processing speeds than sequential generation.
- quote: "Prompt processing — the prefill pass that reads your input before the first token appears — is compute-bound, parallel, and does benefit from more cores and wider vector units."
- url: https://www.compute-market.com/blog/best-cpu-for-local-llm-2026
- source_type: secondary
- published: 2026-09-13
- confidence: high

## Dead ends
- Query: `"llama.cpp" finetune OR training CPU tokens per second` — yielded mostly runtime crashes and generic tutorials warning that CPU fine-tuning of 7B-13B models takes days to weeks, with no standardized tokens/sec training benchmark table.
- Query: `OpenVINO training capabilities` — OpenVINO remains an inference, optimization, and model compression engine; training and backprop must run through PyTorch/IPEX or ONNX Runtime training backends.
- Query: `BLIS LLM training throughput` — BLIS provides BLAS matrix kernels but lacks native automated differentiation frameworks or public end-to-end LLM training benchmarks.

## Suggested follow-ups
- Benchmark micro-model (1M–50M parameter) training throughput with PyTorch CPU Inductor / IPEX under pure bfloat16 AMX vs AVX-512 to measure raw tokens/sec limits.
- Evaluate memory channel scaling effects (dual-channel desktop DDR5 vs quad-channel Strix Halo APU vs octa-channel Xeon/Threadripper) on large-batch compute-bound backprop throughput.
- Investigate whether custom C++/AVX-512 implementations (e.g. specialized tiny-transformer backprops) eliminate framework overhead for sub-minute 1M-token runs.
